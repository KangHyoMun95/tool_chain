# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## tool_chain (Predict Market)

Hệ thống bán **dự đoán AI cho các ván game trên livestream**. Crawler thu thập dữ liệu stream và kết quả từng ván. AI dự đoán cho mỗi ván mới. User đang tham gia stream được **tự động trừ điểm** cho mỗi dự đoán và nhận kết quả realtime qua SSE. Dự đoán sai thì được hoàn điểm.

> Đọc kỹ mục **Quy tắc bất biến về tiền** trước khi sửa bất kỳ code nào đụng tới `balance`, `transactions` hoặc `prediction_subscriptions`.

## Tech stack

Mọi thành phần dùng **bản stable mới nhất**.

| Thành phần | Công nghệ |
|---|---|
| Monorepo | pnpm workspaces |
| API | NestJS (TypeScript) |
| Migration (schema) | Flyway — công cụ **duy nhất** quản lý schema PostgreSQL |
| ORM | TypeORM — **chỉ dùng để truy vấn**, không quản lý schema |
| Database | PostgreSQL |
| Message bus / cache | Redis (Redis Stream cho event, cache id lobby/category/stream) |
| Auth | JWT, session lưu trên Redis |
| Crawler | Python, quản lý dependency bằng pip (`pyproject.toml`) |
| AI predict | Python (`apps/ai/`, thuật toán pattern-v1 trong `src/patterns/`) |
| Frontend | Next.js (web-admin, web-portal) |
| Hạ tầng | docker-compose (cả local và production) |

Dự án **không viết test tự động**. Không tạo file test, không thêm test framework trừ khi được yêu cầu.

### Ranh giới trách nhiệm
- **`web-admin`, `web-portal`**: chỉ có UI. Không đặt business logic, không tính tiền, không lọc quyền ở client.
- **`api`**: nơi duy nhất được đổi `balance`, tạo transaction và quyết định ai nhận event nào.
- **`crawler_v2`**: chỉ thu thập và publish. Không ghi DB trực tiếp. Cấu trúc:
  - `main.py`: `WS_TARGETS = [(tên, host WSS, handler, idle_timeout)]`; **mỗi WSS một handler** (`message_handler.py` cho tgmeq: decode → `SXLobby` → `publish`). Thêm WSS = thêm một dòng vào `WS_TARGETS` + một handler, chuẩn hóa message về đúng `CrawlPayload`. Bật / tắt từng WSS bằng env `WS_ENABLED_<TÊN IN HOA>` (mặc định `true`).
  - **Category Sexy theo `GAME_GROUP_ID_<n>_HANDLER`** (`handlers.REGISTRY`, host WSS `bpcdf.tgmeq.com`; mỗi category một tài khoản riêng): `sx_lobby` (group 1, Baccarat: `SXLobby`, `actual_result` suy từ diff của `winCounts`, `totals` = `winCounts`), `sx_group_2` (Xóc đĩa: `group2_handler.py` + `models/sx_lobby/sx_group_2.py`, `SXGroup2`), `sx_group_3` (Tài xỉu / Sic Bo: `group3_handler.py` + `models/sx_lobby/sx_group_3.py`, `SXGroup3`). Group 2 / 3 dùng chung khung (mỗi bàn một instance, `manage_record` theo `tableID`, `BaseDetection` nhận diện message):
    - **`actual_result` lấy từ `roadInfo.<roads>[0].<field>`** (group 2: `evenOddRoads[0].oddEven`, `RESULT_MAP = {O→L, E→C}`; group 3: `bigRoads[0].bigSmall`, `RESULT_MAP = {Big→T, Small→X, Triple→B}`); phần tử đầu là kết quả của ván `roadInfo.gameRound`, `gameRound` lệch ⇒ null + WARN; roads thiếu / rỗng / thiếu field ⇒ null (bình thường); giá trị lạ ⇒ null + WARN kèm giá trị thô. **`totals` = `roadInfo.winCounts`** lấy trực tiếp theo vị trí `TOTALS_SYMBOLS` (group 2: `(L, C)`; group 3: `(T, X, B)`); message không có winCounts thì giữ totals gần nhất của bàn (để portal không ẩn khung tỉ lệ). Status ánh xạ từ `eventType` ở `STATUS_MAP` (một chỗ), có `STARTING_NEW_ROUND` như SXLobby. roadInfo có thể đến muộn sau khi bàn đã sang ván kế: `(shoe, round)` của kết quả lấy từ chính roadInfo.
    - **Giữ message chờ kết quả** (`_update_hold`): ván đã `GP_WINNER` mà chưa có kết quả (`_pending`) thì `shot_message` trả None (không publish, kể cả message của ván mới đến trước kết quả; state vẫn cập nhật, không đệm) cho tới khi kết quả về, hoặc `GP_NEW_GAME_START` của ván khác (coi như miss kết quả, WARN; miss luôn cả `GP_NEW_GAME_START` thì bỏ cả hai ván, chờ `GP_NEW_GAME_START` ván sau), hoặc quá `PENDING_TIMEOUT_SEC` (60s). Ván đã có kết quả (`_resolved`) không bị giữ.
    - **Cấu hình** (mỗi category một nhóm biến trong `apps/crawler_v2/.env.example`): `GAME_GROUP_ID_<n>` / `_USERNAME` / `_PASSWORD` / `_LOBBY` / `_CATEGORY` / `_HANDLER` / `_ENABLED`. `_LOBBY` / `_CATEGORY` phải trùng `lobby` / `category` trong `config/categories/<tên>.json` (so sau `normalizeName`; dấu tiếng Việt phải giống hệt). `SXGroup2/3(lobby, category)` nhận tham số, không có thì đọc env, thiếu / rỗng ⇒ `ValueError`. Tên category hiện có (đều lobby `casino`): `SEXY - BACCARAT` (B/P/T), `SEXY - XÓC ĐĨA` (C/L, không có hòa), `SEXY - TÀI XỈU` (T/X/B, `B` = bộ ba là `draw`). **Đổi tên category = tạo category mới trong DB** (key `lobby|category|stream` đổi, dữ liệu cũ nằm ở tên cũ).
    - **Thêm một category Sexy mới** (mẫu: PR group 2): (1) `models/sx_lobby/sx_group_<n>.py` (sao từ group 2 / 3, đổi `ENV_*`, key roads / field, `RESULT_MAP`, `TOTALS_SYMBOLS`); (2) `group<n>_handler.py` (decode → `SXGroup<n>` theo `tableID` → `publish`); (3) thêm `"sx_group_<n>"` vào `handlers.REGISTRY`; (4) `config/categories/<tên>.json` (ký hiệu `^[A-Z]$`); (5) nhóm biến `GAME_GROUP_ID_<n>_*` trong `.env.example` (`_ENABLED=false` mặc định); (6) build lại image api + ai. Không cần migration. Chưa sửa `categories.py`: category đang bật mà thiếu biến thì `load_categories` ném `ConfigError` cho cả process.
  - **Mỗi WSS là một task độc lập** (`run_isolated`): lỗi quá ngưỡng (`TooManyFailures`) hoặc lỗi bất ngờ thì **chỉ WSS đó** khởi động lại (backoff 5s → 300s, reset khi đã chạy ổn > 10 phút), không ảnh hưởng WSS khác. Tài khoản / session / `TokenProvider` dùng chung cho mọi WSS.
  - **Lỗi cấp phiên / tài khoản** (`BotCheckError`, `SessionError` = vượt giới hạn login browser hoặc cookie vừa login vẫn bị từ chối): cả process chờ `RESTART_DELAY` (mặc định 600s, tránh dồn dập khi bị check bot) rồi **thoát mã 1**, Docker (`restart: unless-stopped`) chạy lại. Docker stop / SIGINT thoát mã 0.
  - Chưa kiểm tra giới hạn kết nối / tài khoản của server: nhiều WSS cùng một tài khoản có thể đá nhau.
- **`ai`**: chỉ ĐỌC DB (`game_sessions`, để dựng lại bảng đếm) và ghi Redis của riêng nó + stream `predict:results`. **Không** ghi bảng nghiệp vụ nào trong DB, không đổi `balance`, không ghi `prediction_subscriptions` hay `transactions`. AI trả kết quả về `api` qua Redis Stream; `api` lưu DB và đẩy SSE (billing sau này cũng nằm ở `api`). `api` là nơi duy nhất sinh `key_id`, `game_session_id` và ghi DB.
- **Lưu ý độ trễ:** AI **không** chờ DB: `api` phát `predict:requests` ngay khi thấy tick `IN_PROGRESS` đầu tiên của ván và đưa kết quả các ván trước qua `ai:results` / `recent:*` (Redis), nên không phụ thuộc batch ghi DB (tối đa 3s). DB chỉ dùng để dựng lại bảng đếm lúc AI khởi động.
- Auth: xem mục **Auth & bảo mật** bên dưới.

### Contract dùng chung
`apps/crawler_v2/contract.py` và `packages/shared/src/realtime.ts` mô tả **cùng một schema event**. Sửa một bên thì **bắt buộc** sửa bên kia trong cùng một commit.

Tương tự `packages/shared/src/ai.ts` và `apps/ai/src/patterns/contract.py` mô tả **cùng một schema** cho 3 stream dự đoán (`predict:requests`, `ai:results`, `predict:results`, `schema_version: 1`, mỗi entry một field `payload` là JSON), kèm namespace UUIDv5 của `prediction_id`. Cùng quy tắc: sửa một bên thì sửa bên kia trong cùng commit.

**Ký hiệu kết quả không còn cố định B/P/T.** Mỗi ký hiệu (`actual_result`, `pick`, khóa của `totals` / `counts` / `pct`) là **đúng một chữ in hoa** (`^[A-Z]$`); tập hợp lệ của từng category nằm ở `config/categories/*.json` (xem **File định nghĩa category**). `predict:results`: `pick: string | null`, `detail.rows` / `chosen` dạng dict: `rows: [{k, pattern, counts: {ký_hiệu: n}, pct: {ký_hiệu: 0..1|null}, total, eligible}]`, `chosen: {k, pattern, occurrences, pct: {ký_hiệu: 0..1}}` (khóa = `predictable` của category). Tick: `totals?: Record<ký_hiệu, number>` thay `total_B/P/T`.

## Luồng dữ liệu

### Luồng 1 — Kết quả từ crawler (đã có)
```
crawler_v2 ──publish──► Redis Stream ──► api consumer
                                             ├─► realtime.hub  → SSE xuống web-portal (lọc theo key_id; tick / round_result CHỈ ĐI TỚI)
                                             └─► tick-persister → ghi DB theo batch (MAX_BATCH dòng hoặc MAX_WAIT_MS, xem ingestion/ingestion.constants.ts)
```

### Phiên và kết quả CHỈ ĐI TỚI (luồng đẩy xuống portal)
Tick muộn của ván trước (vd `SUMMARY_RESULT` của round N−1) thường đến **sau** tick đầu của round N. Portal **không bao giờ được lùi phiên**.
- **Hàm so vị trí dùng chung** (`packages/shared/src/realtime.ts`): `Position {shoe, round}`, `ShoeContext {current, previous}`, `comparePosition(incoming, ref, ctx)` → -1 / 0 / 1, `advanceShoe(ctx, shoe)`, `payloadPosition(data)`. Cùng shoe ⇒ chỉ so round (**không** có quy tắc "round tụt = reset": round chỉ reset khi đổi shoe). Khác shoe ⇒ so hạng: shoe chưa thấy = 3 (shoe mới; **không** giả định số shoe tăng dần), `current` = 2, `previous` = 1, shoe cũ khác = 0. Hub, ShoeObserver và portal dùng **chung** hàm này; không tự viết lại logic so vị trí.
- **Hub** (`realtime/realtime.hub.ts`), state trong RAM theo `key_id` (ShoeContext, con trỏ phiên, con trỏ kết quả, `lastTick`), cập nhật cho **mọi** tick kể cả stream không ai xem, không nạp sẵn lúc khởi động (tick đầu tiên khởi tạo). Trong một tick: xét con trỏ phiên trước, rồi mới xét kết quả.
  - Event `tick`: vị trí ≥ con trỏ phiên ⇒ cập nhật (`advanceShoe` nếu shoe mới) và đẩy; cũ hơn ⇒ **không đẩy** (kể cả status, totals, player_count, time).
  - Event `round_result` (`RealtimeRoundResult {type, item_id, stream_id, shoe, round, result, ts}`): `actual_result` là B/P/T **và** vị trí **mới hơn** con trỏ kết quả ⇒ đẩy một lần; còn lại bỏ (không lấy kết quả ván lùi, không đẩy trùng). Kết quả ván bị bỏ qua được portal lấy lại từ DB khi refetch lịch sử.
  - Snapshot khi mở kết nối: `lastTick` hub đã chấp nhận; hub chưa có state (vừa restart) mới dùng `latest:{key_id}` (portal tự chặn nếu là ván cũ).
  - Tick không đọc được shoe/round: chuyển tiếp như cũ, không lọc, không `round_result`.
  - **Tự phục hồi:** stream chỉ nhận tick cũ hơn liên tục trong `HUB_STALE_RESET_MS` (mặc định 60000) ⇒ xóa state của stream (cả hai con trỏ), log WARN, tick kế tiếp khởi tạo lại. Giữ tối đa `HUB_STATE_MAX` (1000) stream, quá thì bỏ stream lâu không có tick nhất (LRU theo thời gian tick, log WARN).
  - Việc lọc **chỉ** áp dụng cho SSE: TickPersister (group `persist`) và PredictTriggerService (group `predict-trigger`) đọc `ticks` độc lập, nhận đủ mọi tick.
- **Portal** (`useLiveItems`): bộ theo dõi vị trí cho mỗi item, sống qua các lần kết nối lại; tick cũ hơn phiên đang hiển thị ⇒ bỏ; `round_result` không mới hơn kết quả đã nhận ⇒ bỏ. Trạng thái trực tiếp (status, tổng B/P/T, số người chơi, time) chỉ lấy từ `tick` đã qua bộ lọc; kết quả / lịch sử / đúng-sai **chỉ** lấy từ `round_result`. `NEXT_PUBLIC_SHOW_STREAM_DEBUG=true` ⇒ `console.debug` khi bỏ tick (vị trí tick và vị trí đang hiển thị), khi nhận `round_result`, `prediction`, và khi đổi phiên.

### Luồng 2 — Dự đoán
Đã làm (chưa có billing, xem mục **Luồng dự đoán AI** bên dưới):
```
crawler → Redis "ticks" → api (PredictTriggerService)
   ├─ tick IN_PROGRESS đầu tiên của ván → predict:requests ─► AI ─► predict:results ─► api (PredictResultConsumer)
   └─ tick đầu tiên có actual_result    → recent:* + ai:results ─► AI (cập nhật bảng đếm)
                                                      api: kiểm tra hạn chót → lưu predictions (DB) → SSE public
```
Billing (xem mục **Billing** bên dưới):
```
prediction mới có pick → trừ tiền participant (cùng transaction với INSERT prediction)
ingestion ghi result + FINISHED (commit) ─┐
job hủy ván RUNNING quá X phút → CANCELLED ┼─► settle:requests ─► SettlementConsumer → hoàn tiền (refunded_at IS NULL)
sweeper (mỗi phút, gửi bù tín hiệu bị mất) ┘
```
Participant = kết nối SSE tham gia trong `ConnectionRegistry` (xem **Participants & SSE**); pick chỉ giao cho user đã trừ.
Portal: xem **Stream detail realtime** (kết nối SSE) và **Dữ liệu web-portal** (khóa thẻ bàn).

### key_id, payload crawler & ingestion
- `key_id` = `<lobby_name>|<category_name>|<stream_name>` đã chuẩn hóa. **Chỉ là khóa cache / phòng realtime (`item_id` của tick), KHÔNG lưu DB** (không có cột `streams.key_id`). Tên chứa `|` bị coi là tick lỗi.
- **Chuẩn hóa tên** (`normalizeName()` ở `common/normalize.ts`, `normalize_name()` ở `contract.py`): trim, gộp khoảng trắng liên tiếp thành 1, lowercase. **Chỉ để chống trùng, không lưu**; DB lưu tên đã trim của lần gặp đầu. Chống trùng bằng unique index trên biểu thức (không có cột `*_norm`), biểu thức SQL phải khớp `normalizeName()`: lobbies `(norm(lobby_name))`, categories `(lobby_id, norm(category_name))`, streams `(category_id, norm(stream_name))`. Upsert: `INSERT ... ON CONFLICT (<biểu thức>) DO NOTHING`, rồi SELECT lại id.
- Cache id (RAM + Redis, ghi sau khi DB commit): `lobby:{norm}`, `category:{lobby_id}:{norm}`, `stream:{key_id}`. Chỉ chạm DB khi cache miss. Mọi thứ bên trong sau đó dùng **`stream_id`**.
- **Payload crawler** (`CrawlPayload`, `contract.py` ↔ `realtime.ts`), gửi liên tục, nhiều lần cho cùng một ván: `lobby_name, category_name, stream_id, stream_name, stream_shoe, stream_round, streamer_id, player_count, player_value, status, actual_result, totals`.
  - **Ghi DB**: tên lobby/category/stream, `stream_shoe` (số nguyên như `stream_round` → cột `game_sessions.road_shoe`), `stream_round` (số nguyên → `game_sessions.road_count`), `streamer_id` (→ `stream_information`), `actual_result` (→ `game_sessions.result`; phải thuộc `results` của category, xem **File định nghĩa category**).
  - **Chỉ hiển thị** (chỉ qua realtime/SSE, không ghi DB): `player_count, player_value, status, totals`, `streamer_name`, `streamer_country` và 5 trường time `deliver_time, timestamp, stamp_time, round_start_time, repaint_time` (`str | None`, optional; crawler gửi qua Redis Stream nên không có DTO; ingestion bỏ qua, không có cột/migration). `stream_id` là id text phía nguồn, bỏ qua. Ingestion không đọc `status` của payload để suy ra trạng thái.
- **Khóa duy nhất của game_session** là `(stream_id, road_shoe, road_count)` (round có thể reset khi đổi shoe nên `(stream_id, road_count)` không đủ). `stream_round` của payload = `road_count`, `stream_shoe` của payload = cột `road_shoe` (payload đặt tên `stream_*`, cột DB đặt tên `road_*`); `stream_shoe` cũng là số nguyên (nhận number hoặc chuỗi số). `stream_shoe` hoặc `stream_round` thiếu / không phải số nguyên ⇒ tick bị bỏ qua cả phần ghi DB (log, tối đa 1 lần/phút cho mỗi stream + lý do); luồng realtime không bị ảnh hưởng.
- **`game_session_id`** = UUIDv5 xác định từ `key_id + "|" + road_shoe + "|" + road_count` với namespace cố định (`game-sessions/game-session-id.ts`, không được đổi). Cùng ván luôn ra cùng ID. Insert `ON CONFLICT DO NOTHING`, không set `status` (mặc định `RUNNING`; trừ việc set `FINISHED` khi có result, status của stream / game_session do job khác quản lý). Gộp trong batch theo `(stream, road_shoe, road_count)`.
- **Log quan sát shoe** (`ingestion/shoe-observer.ts`, chỉ log, không đổi hành vi ghi), dùng `comparePosition`: tick cũ hơn vị trí lớn nhất ⇒ không log, không cập nhật; INFO khi shoe của stream đổi (kèm ghi chú nếu shoe đó đã thấy trước đó). Không còn WARN "round giảm" (tick muộn là bình thường); WARN về vị trí chỉ có ở cơ chế tự phục hồi của hub. Trạng thái gần nhất lưu Redis `stream_last:{key_id}` (hash shoe/round/prev_shoe) và `stream_shoes:{key_id}` (set shoe đã thấy), TTL 24h.
- **Ghi `result` và set `FINISHED` trong cùng một câu UPDATE** (atomic): `UPDATE game_sessions SET result = ?, status = 'FINISHED' WHERE game_session_id = ? AND result IS NULL AND status <> 'CANCELLED'`. **Không bao giờ ghi đè `result`**: tick báo result khác result đã lưu → log cảnh báo, giữ nguyên. Ván `CANCELLED` nhận result → không cập nhật, log WARN (kèm stream, shoe, round). Đây là chuyển trạng thái **duy nhất** ingestion được làm (RUNNING → FINISHED); `FINISHED` là trạng thái cuối, không được đổi lại; các chuyển trạng thái khác (vd `CANCELLED`) do job kiểm tra status quản lý.
- `stream_information`: một dòng cho mỗi stream (unique `stream_id`), chỉ ghi khi `streamer_id` đổi.
- Batch: gộp tick theo `(stream, stream_round)` giữ bản mới nhất (giữ result nếu có), ghi theo thứ tự lobbies → categories → streams → stream_information → game_sessions trong **một DB transaction**, chỉ `XACK` sau khi commit. Tick lỗi validate: log, bỏ qua (vẫn XACK). Lỗi DB: giữ buffer, thử lại.

### File định nghĩa category (`config/categories/*.json`)
Mỗi category một file (tên file tùy ý), nằm trong repo và **đóng vào image** của api và ai (Dockerfile COPY, không mount). Thư mục đọc: env `CATEGORY_CONFIG_DIR`, bỏ trống ⇒ `config/categories` ở thư mục chạy (docker: `/app`) hoặc ở gốc repo. api nạp lúc khởi động (`apps/api/src/category-config/`, zod `.strict()`); AI cùng luật (`apps/ai/src/patterns/category_config.py`, pydantic `extra="forbid"`; mọi lệnh `python main.py ...` đều nạp trước, sai ⇒ in tất cả lỗi và thoát mã 1). **Sửa luật ở một bên thì sửa bên kia trong cùng commit.** Container AI build từ gốc repo (`context: .`, `dockerfile: apps/ai/Dockerfile`) để COPY `config/`.
```json
{ "lobby": "casino", "category": "bacarat",
  "results": { "B": {"label": {"vi": "B", "en": "B"}, "color": "#DC2626"}, "P": {...}, "T": {...} },
  "predictable": ["B", "P"], "ignore_in_pattern": ["T"], "draw": ["T"], "totals": ["B", "P", "T"] }
```
- `lobby`, `category`: tên khớp (sau `normalizeName`) với tên trong tick; không trùng giữa các file. `results`: mọi ký hiệu hợp lệ, mỗi ký hiệu bắt buộc `label.vi`, `label.en`, `color` (`#RRGGBB`), không trường nào khác. `predictable`: ký hiệu AI được chọn làm pick (không rỗng). `ignore_in_pattern`: AI bỏ qua khi dựng chuỗi. `draw`: hiển thị / thống kê là "hòa" (**không ảnh hưởng tiền**). `totals`: ký hiệu hiển thị trong khung tỉ lệ (số lấy từ `tick.totals`, portal không tự đếm).
- **Luật kiểm tra (api KHÔNG khởi động nếu sai, in TẤT CẢ lỗi một lần: tên file, đường dẫn trường, lỗi gì):** đủ mọi khóa (`lobby, category, results, predictable, ignore_in_pattern, draw, totals`); không có khóa lạ; ký hiệu `^[A-Z]$`; `predictable / ignore_in_pattern / draw / totals ⊆ results`, không trùng trong một mảng; `predictable ∩ ignore_in_pattern = ∅` và `predictable ∩ draw = ∅`; `predictable` không rỗng (3 mảng còn lại được rỗng nhưng phải có mặt); thư mục không có file `.json` ⇒ lỗi; trùng (lobby, category) ⇒ lỗi.
- **Từ chối tick (api, `CategoryConfigService.inspectTick`):** tick của category **không có file**, hoặc `actual_result` không thuộc `results` ⇒ ingestion không ghi DB, hub không đẩy SSE (kể cả snapshot `latest:*`), predict-trigger không ghi `round_status` / `recent` / `ai:results` / `predict:requests`; log ERROR (tối đa 1 dòng / phút / khóa), API không dừng. `predict:results` có `pick` ngoài `predictable` ⇒ bỏ như message sai contract.
- **Cấp cho portal:** `GET /api/streams/:id` kèm `result_config` (portal đọc ở `Stream.resultConfig`; hạt / pill / nhãn / màu / đúng-sai-hòa đều theo đó, không hardcode ký hiệu) (`{results, predictable, draw, totals}`, null nếu category không có file); `GET /api/categories/:id/stream-stats` trả `{ items, result_config }`.
- **Thêm category mới:** (1) thêm `config/categories/<tên>.json`; (2) crawler gửi đúng `lobby_name` / `category_name` và ký hiệu thuộc `results`; (3) build lại image api (+ ai). Không cần migration.
- Tiền không đọc cấu hình này: hoàn tiền vẫn là `g.result <> p.predict_result` hoặc ván `CANCELLED`; `draw` chỉ quyết định nhãn "hòa" và cách thống kê (thắng = pick trùng result; kết quả thuộc `draw` là hòa).

### Luồng dự đoán AI (pattern-v1)
- **3 Redis Stream** (contract ở `packages/shared/src/ai.ts` ↔ `apps/ai/src/patterns/contract.py`, `MAXLEN ~ 10000`):
  - `predict:requests` — api ghi, AI đọc: `{game_session_id, stream_id, key_id, shoe, round, requested_at}`.
  - `ai:results` — api ghi, AI đọc: `{game_session_id, stream_id, key_id, shoe, round, result B|P|T, received_at}`.
  - `predict:results` — AI ghi, api đọc: `{prediction_id, game_session_id, stream_id, key_id, shoe, round, pick B|P|null, confidence 0–1, chosen, detail[], history_used, missing_previous, half_life_minutes, shoe_weight, reason, model_version, created_at}` (`detail[].counts` / `total` và `chosen.occurrences` là số có trọng số, số thực; `half_life_minutes` / `shoe_weight` null khi tắt trọng số). `reason` ∈ `OK | NOT_ENOUGH_HISTORY | NO_ELIGIBLE_SUFFIX`; `pick` khác null khi và chỉ khi `reason = OK`. `prediction_id` = UUIDv5(`PREDICTION_NAMESPACE`, `game_session_id`), không đổi namespace.
- **Redis key và chủ sở hữu (chỉ chủ sở hữu được ghi):**
  - api: `round_status:{game_session_id}` (status mới nhất, **chỉ tiến** IN_PROGRESS < DONE < GET_RESULT < SUMMARY_RESULT, TTL 1h), `predict_req:{game_session_id}` (cờ đã phát yêu cầu, TTL 1h), `recent:{stream_id}:{shoe}` (HASH round → result B/P/T, `HSETNX` nên không ghi đè, TTL 24h).
  - AI: `ai:counts:{stream_id}` (HASH `"<pattern>|<ký hiệu predictable>"` → số lần), `ai:wcounts:{stream_id}` (HASH cùng khóa, giá trị float = số lần có trọng số, tính từ mốc `t0` = lúc AI dựng lại bảng đếm gần nhất, nên không có ý nghĩa tuyệt đối), `ai:wcounts:{stream_id}:{shoe}` (như trên nhưng chỉ shoe đó, TTL 6 giờ, cập nhật trong cùng script Lua; rebuild chỉ dựng cho shoe hiện tại của mỗi bàn), `ai:wstate` (HASH `{t0, half_life_minutes}` đang dùng cho các bảng có trọng số; rỗng = tắt), `ai:counted:{stream_id}:{shoe}` (SET game_session_id đã đếm, TTL 48h).
  - Các bước nhiều lệnh là **script Lua** (atomic): `advanceRoundStatus`, `recordResult` (`HSETNX` + `EXPIRE` + `XADD ai:results`, chỉ XADD khi HSETNX thêm mới), `requestPrediction` (`SET NX EX` + `XADD predict:requests`), và `count` phía AI (`SADD` đã đếm + `HINCRBY`).
- **Consumer group** (tên consumer cố định, đọc PEL trước): api `predict-trigger` (trên `ticks`) và `predict-persist` (trên `predict:results`); AI `ai-counter` (trên `ai:results`) và `ai-predictor` (trên `predict:requests`). Tạo group ở `$` (tạo ở `0` sẽ replay lịch sử). `predict-trigger` bỏ qua **chỉ bước phát `predict:requests`** với tick cũ hơn 30s (tính theo thời gian trong ID message của stream); `round_status`, `recent`, `ai:results` vẫn xử lý khi replay.
- **Hạn chót:** api chỉ lưu và đẩy prediction khi `round_status` của ván vẫn là `IN_PROGRESS` (không tồn tại cũng coi là quá hạn). Quá hạn ⇒ log INFO JSON `{"event":"late_prediction", key_id, stream_id, shoe, round, status, age_ms}` (dùng để đếm tần suất), không lưu. AI cũng bỏ qua request khi ván đã `DONE` trở đi.
- **Thuật toán pattern-v1** (hàm thuần `choose_pick` trong `apps/ai/src/patterns/pattern.py`, dùng chung bởi service và backtest): chuỗi của một (stream, shoe) sắp theo round, **bỏ các ký hiệu `ignore_in_pattern`** của category (config, không còn hardcode T), không nối qua shoe; bảng đếm tách theo từng stream (gộp mọi shoe của stream). Với đuôi k = 3..10 của tối đa 10 kết quả gần nhất trong shoe hiện tại: `total` = tổng số lần của các ký hiệu **`predictable`**; đuôi hợp lệ khi `total ≥ 3` và ký hiệu nhiều nhất là **duy nhất** (2 ký hiệu thì tương đương `count_x ≠ count_y`). Pick chỉ trong `predictable`. **Trọng số theo độ mới** (cấu hình ở bảng `job_configs`, xem dưới; `AI_HALF_LIFE` NULL = tắt ⇒ chạy đúng pattern-v1 như mô tả này, không dùng trọng số / hệ số shoe): mỗi lần một pattern xuất hiện có trọng số `2^(-tuổi / half-life)` (tuổi = thời gian từ lúc ván ra kết quả); số đếm của đuôi cho ký hiệu R là `W[R] = W_bàn[R] + (AI_SHOE_WEIGHT − 1) × W_shoe_hiện_tại[R]` (bảng có trọng số của cả bàn và của riêng shoe của ván đang dự đoán). **Điều kiện có dự đoán:** tổng số lần THẬT (`ai:counts`) ≥ 3; ký hiệu nhiều nhất DUY NHẤT theo `W`; tổng `W` > 0. **Chọn hoàn toàn theo `W`; `confidence` và `chosen.pct` được co về đều nhau `p' = (1 - c)/m + c·p` (`WEIGHTED_CONFIDENCE_SCALE` c = 0.5, m = số ký hiệu `predictable`; 100% → 75%) vì % có trọng số gần như luôn ~100% (trung vị confidence khoảng 0.7–0.8; `detail` giữ % chưa co; tắt trọng số thì không co)** (trước đây hiển thị theo `W` trực tiếp) (không trộn với tỉ lệ số lần thật): % của ký hiệu nhiều nhất cao nhất → tổng `W` lớn hơn → k ngắn hơn; `confidence` = % đó. Ít mẫu thật nhưng gần đây có thể ra % rất cao: đã chấp nhận (điều kiện ≥ 3 lần thật vẫn giữ). **`detail` chỉ lưu số có trọng số** (`counts`, `total`, `pct` của PatternRow; `chosen.occurrences` = tổng `W`), đã chuẩn hóa để một kết quả vừa xảy ra = 1 ("lần hiệu dụng"), KHÔNG lưu số lần thật; `predict:results` / `predictions.detail` kèm `half_life_minutes` và `shoe_weight` đã dùng (cả hai `null` khi tắt trọng số; khi đó `counts` / `total` chính là số lần thật). **Contract `predict:results` đổi (số thực, thêm `half_life_minutes` / `shoe_weight`, API từ chối message thiếu hai trường này) ⇒ API và AI PHẢI deploy cùng nhau** (message cũ còn trong stream lúc chuyển sẽ bị bỏ). Chọn % của ký hiệu nhiều nhất cao nhất → `total` lớn hơn → k ngắn hơn. `confidence` = % đó (0–1). Dưới 3 kết quả ⇒ `NOT_ENOUGH_HISTORY`; không có đuôi hợp lệ ⇒ `NO_ELIGIBLE_SUFFIX` (đều `pick = null`). Cập nhật bảng đếm khi có kết quả **thuộc `predictable`** (ký hiệu khác không đếm): với mỗi k có đủ k kết quả ngay trước trong cùng shoe thì `+1` cho `"<k kết quả trước>|<kết quả>"` (pattern nối liền các ký tự, ký hiệu đúng 1 chữ in hoa). AI tra cấu hình theo `key_id` của `predict:requests` / `ai:results`; **category không có file ⇒ không dự đoán, không đếm, log ERROR** (1 dòng / phút / category); `ai:results` có `result` ngoài `results` ⇒ bỏ qua, log ERROR.
- **Mô hình hình dạng (`apps/ai/src/patterns/shape_model.py`, trộn vào pattern-v1):** tự học, không có hình viết sẵn. Mọi đuôi k = 3..10 (đã bỏ `ignore_in_pattern`, cùng shoe) là một hình, gộp hai chiều ký hiệu; mô hình đếm theo category (gộp mọi stream, chỉ category có ĐÚNG 2 `predictable`), nằm trong RAM của AI: dựng từ DB lúc khởi động và mỗi lần `rebuild_now`, cập nhật khi đếm được ván mới (cùng điều kiện `ai:counted`). Chỉ hình có `n >= AI_SHAPE_MIN_N` (30) và `|z| >= AI_SHAPE_Z` (3.0) mới được dùng; nhiều hình khớp thì **ưu tiên đuôi dài nhất** (duyệt k từ 10 xuống 3, lấy hình đầu tiên đủ bằng chứng, không còn chọn theo |z| lớn nhất); khi có hình VÀ pattern-v1 có pick thì `pct' = (1 - w) * pct + w * [x == pick của hình]` (`w = AI_SHAPE_WEIGHT`, mặc định 0.2; **0 = tắt**; hình cùng hướng với pattern-v1 (đã co về 0.75) ⇒ confidence ~0.8; trần `MAX_CONFIDENCE` vẫn 0.9) trên dòng được chọn: `pick`, `confidence`, `chosen.pct` đổi; `detail.rows` giữ số của pattern-v1; hòa ⇒ giữ pick pattern-v1. Ván không có hình giữ NGUYÊN pattern-v1. Ván có áp dụng hình có `model_version = "pattern-v1+shape:<dạng chuẩn>"` (vd `pattern-v1+shape:1221`) và log AI in dòng `hình ...` (pick / % trước và sau trộn). Không đổi contract. Backtest: `python main.py backtest --shape-model Z,Z`. Chưa kiểm chứng trên dữ liệu thật (xem `apps/ai/README.md`).
- **Nguồn history của AI** (`AiService._history`, `apps/ai/src/patterns/service.py`): giữ vòng chờ round − 1 trong `recent:{stream_id}:{shoe}`; sau đó nếu HASH vẫn thiếu **bất kỳ** round nào trong 1..round−1 (vd Redis restart giữa shoe) ⇒ đọc thêm (read-only, `asyncio.to_thread`) `game_sessions` có result của đúng `(stream_id, road_shoe)`, `road_count < round`, `created_at` trong `AI_HISTORY_DB_WINDOW_HOURS` giờ gần nhất (mặc định 6; số shoe có thể lặp lại giữa các ngày). Gộp theo round (HASH ưu tiên) rồi `history_before` bỏ T, lấy 10 phần tử cuối. **Không** ghi ngược vào HASH. Log dự đoán kèm `history=redis` | `history=redis+db (+n round)` | `history=redis (db lỗi)`.
- **AI dựng lại bảng đếm** từ DB (game_sessions `FINISHED`, JOIN `streams` / `categories` / `lobbies` để tra cấu hình; stream của category không có file bị bỏ qua, log ERROR) lúc khởi động, trước khi consume (restart để dựng lại; dựng cả `ai:wcounts` và bảng shoe hiện tại, trọng số theo `COALESCE(ended_at, created_at)` của ván; đường realtime dùng `received_at` của `ai:results` (lúc api thấy kết quả đầu tiên): hai mốc lệch nhau tối đa vài giây (batch ghi DB ≤ 3s + lệch đồng hồ), vô nghĩa so với bán rã tính bằng phút. **Dựng lại giữa chừng không cần restart và NGUYÊN TỬ:** `AI_HALF_LIFE` đổi trong DB, hoặc số mũ trọng số live `(ts − t0) / half-life` vượt `MAX_WEIGHT_EXPONENT` = 900 (float64 chịu tới ~1023; script Lua đếm trả số mũ về cho AI) ⇒ AI dựng TOÀN BỘ `ai:counts` / `ai:wcounts` / bảng shoe / `ai:counted` của MỌI stream vào key tạm `ai:tmp:{run}:...` với MỘT `t0` mới, xong hết mới đổi tất cả key + `ai:wstate` (`{t0, half_life_minutes}`) trong một MULTI/EXEC. Lỗi giữa chừng ⇒ xóa key tạm, bảng và `t0` cũ giữ nguyên, log ERROR, thử lại sau 60s. `t0` và bán rã nằm trong Redis (`ai:wstate`), đổi cùng lúc với bảng; dự đoán đọc bảng + `ai:wstate` trong cùng một transaction và script Lua đếm đọc `ai:wstate` trong script, nên không bao giờ lệch `t0`. **Trong lúc dựng lại KHÔNG chặn dự đoán** (vẫn chạy bằng bảng và `t0` cũ tới lúc đổi bảng); chỉ tạm dừng phần ĐẾM kết quả mới (`ai:results` nằm lại trong stream): AI chờ handler đếm đang chạy dở, chờ 5s cho ingestion ghi nốt batch cuối, đọc DB, đổi bảng, rồi đếm tiếp (ván đã trong DB bị loại bởi `ai:counted`). Ngưỡng 900 half-life = 18,75 ngày với bán rã 30 phút, 37,5 ngày với 60 phút. `AI_SHOE_WEIGHT` đổi chỉ áp dụng ngay, không dựng lại; `python main.py verify` chỉ so `ai:counts`, không so `ai:wcounts`; `python main.py backtest --half-life <phút> --shoe-weight <n>` để so sánh với pattern-v1 (bỏ `--half-life` = tắt)). `python main.py verify` so Redis với đếm brute-force từ DB. Backtest: `python main.py backtest` (baseline = ký hiệu `predictable` xuất hiện nhiều nhất (duy nhất) trong lịch sử stream; ván có kết quả thuộc `draw` không tính đúng/sai; xem `apps/ai/README.md`; kết quả đo gần nhất cho thấy pattern-v1 chưa hơn baseline và `confidence` không phản ánh tỉ lệ đúng, nên chưa dựa vào nó để thu phí/quảng cáo).
- **Lưu DB:** bảng `predictions` (V9): `predict_result` cho phép NULL (CHECK định dạng `^[A-Z]$` từ V19; pick thuộc `predictable` của category do ứng dụng kiểm tra), `detail jsonb` = `{chosen, rows, history_used, missing_previous, half_life_minutes, shoe_weight}` (counts / total của rows là số có trọng số, không có số lần thật; dòng cũ trước khi có trọng số không có hai khóa cuối), `model_version`, `reason`; CHECK: có `predict_result` khi và chỉ khi `reason = 'OK'`, `confidence_score` trong 0..1. Trước khi insert, api `INSERT game_sessions ... ON CONFLICT DO NOTHING` trong cùng transaction (khóa ngoại; ván có thể còn trong batch của ingestion), rồi `INSERT predictions ... ON CONFLICT (game_session_id) DO NOTHING RETURNING`; chỉ khi thêm dòng mới mới đẩy SSE.
- **SSE prediction:** event `type: "prediction"` (`RealtimePrediction` ở `packages/shared`, không chứa `detail`) **không đi kênh public**. Sau khi transaction (insert + trừ tiền) commit, `PredictionDeliveryService`: pick != null ⇒ chỉ gửi lên kết nối tham gia của user có `prediction_subscriptions` chưa giao (`delivered_at IS NULL`, đọc từ DB nên xử lý lại message vẫn giao đúng người) rồi set `delivered_at`; pick = null ⇒ gửi cho mọi kết nối tham gia của stream. Tick có `type: "tick"` (client coi event thiếu `type` là tick) và vẫn public theo `key_id`. Pick của ván đã kết thúc chỉ lộ qua API đọc đã lọc `FINISHED` (history, stats, stream-stats).
- **API đọc:** `GET /api/streams/:id/predictions/current` — prediction mới nhất của stream (theo thời điểm tạo) kèm `shoe`, `round`, `confidence` 0–1, không có `detail`, có `locked`; phạm vi nhìn thấy như `GET /streams/:id`; 404 khi chưa có prediction. Ván còn `RUNNING` có pick: chỉ user đã bị trừ tiền cho ván đó nhận pick (`locked: false`, và set `delivered_at` nếu chưa có), người khác (kể cả HOST / ADMIN, user vào giữa ván) nhận `{ locked: true, prediction_id, game_session_id, stream_id, shoe, round, created_at }` (portal: "Dự đoán từ ván sau"). Ván `FINISHED` / `CANCELLED` hoặc pick = null ⇒ công khai. Portal phải so `(shoe, round)` với ván đang xem.

### Billing (trừ tiền / hoàn tiền) — `apps/api/src/billing/`
- **Phí:** env `PREDICTION_FEE` (số nguyên > 0, bắt buộc; thiếu / sai thì API dừng). `fee_amount` lưu giá lúc trừ. Chỉ role **USER** bị trừ.
- **Trừ tiền** (`BillingService.charge`, gọi trong transaction của `PredictionsService.insertFromResult`): chỉ khi INSERT prediction thêm dòng MỚI và `pick != null`. Snapshot user_id DISTINCT của participant (`ConnectionRegistry.participantUserIds`) lấy ngay trước transaction (vào sau thời điểm này ⇒ không trừ, không có pick ván đó). Thứ tự: `SELECT ... FROM game_sessions ... FOR SHARE` (ván phải còn `RUNNING`, nếu không thì không trừ — để settlement không thể chạy xong trước khi subscription commit) → khóa users `ORDER BY user_id FOR UPDATE` → `UPDATE users ... WHERE balance >= fee AND status = 'ACTIVE' AND role USER RETURNING` → `prediction_subscriptions` (`ON CONFLICT DO NOTHING`, số dòng phải bằng số user bị trừ, lệch ⇒ ném lỗi rollback) → `transactions CHARGE`. Participant không trừ được trả về `rejected` (`INSUFFICIENT_BALANCE` / `NOT_ALLOWED`); sau commit: `INSUFFICIENT_BALANCE` ⇒ event `insufficient_balance` rồi đóng kết nối (close_reason `INSUFFICIENT_BALANCE`), `NOT_ALLOWED` ⇒ đóng `SESSION_REVOKED`.
- **Cổng chặn (402 `{ code: "INSUFFICIENT_BALANCE" }`, `BillingService.assertCanParticipate`, so sánh trong SQL):** `GET /api/streams/:id` với USER không đủ điểm, và `POST /api/realtime/ticket` có `participate_stream_id`. `GET /api/auth/me` trả `can_participate` (USER, ACTIVE, `balance >= PREDICTION_FEE`, tính trong SQL) để portal khóa thẻ bàn — portal không tự so balance với phí.
- **Settlement:** stream `settle:requests` (`packages/shared/src/settle.ts`, field `payload` = JSON `{schema_version: 1, game_session_id, reason: FINISHED|CANCELLED}`, `MAXLEN ~ 10000`), group `settle`, `SettlementConsumer` (PEL trước rồi `>`, timeout mỗi tin, XACK sau commit). **Chỉ tạo message bằng `buildSettleMessage()` và chỉ đọc bằng `parseSettleMessage()`**, không tự ghép field; nơi gửi duy nhất là `SettleQueue` (ingestion, job hủy ván, sweeper gọi qua nó), message được parse lại trước khi XADD (sai ⇒ log ERROR tại chỗ, không XADD). Settlement chỉ cần `game_session_id` + `reason`, phần còn lại đọc từ DB. Consumer gặp message sai contract ⇒ log ERROR kèm toàn bộ field, chép sang `settle:dead` (`MAXLEN ~ 1000`, field `source_id, error, fields, dead_at`) rồi mới XACK (XADD `settle:dead` lỗi thì không XACK, thử lại). `BillingService.refund`: một transaction — chọn subscription `refunded_at IS NULL` của ván `CANCELLED` hoặc `FINISHED` có `result <> predict_result` (kết quả `T` luôn được hoàn) `FOR UPDATE OF ps` → khóa users theo `user_id` tăng dần → một câu CTE: set `refunded_at`, cộng `fee_amount`, ghi `transactions REFUND` (balance_before / after từ RETURNING). Hoàn cho cả user đã DEACTIVE / DELETED. Idempotent: chạy lại không hoàn trùng.
- **`HAS_REFUND`** (env `"true"|"false"`, mặc định `true`): luồng settlement (ingestion / job hủy ván / sweeper → `settle:requests` → `SettlementConsumer`) chạy như nhau ở cả hai giá trị; chỉ bước cuối của `BillingService.refund()` khác: `true` ⇒ hoàn tiền; `false` ⇒ set `prediction_subscriptions.refund_waived_at = now()` (V12) cho các subscription đủ điều kiện, không đổi balance, không ghi transactions (WARN lúc khởi động). Subscription "chờ quyết định" = `refunded_at IS NULL AND refund_waived_at IS NULL` (CHECK: không thể vừa hoàn vừa bỏ hoàn); mọi truy vấn chọn subscription để hoàn (refund, sweeper, job hủy ván) PHẢI lọc cả hai cột. Bật lại `true` không hoàn bù ván đã bỏ hoàn; quyết định theo giá trị cờ **lúc settlement xử lý** (tín hiệu còn trong hàng đợi lúc đổi cờ sẽ theo giá trị mới).
- **Nguồn tín hiệu:** ingestion gửi sau khi batch COMMIT cho các ván vừa được set result + FINISHED (RETURNING của câu UPDATE; lỗi Redis chỉ log, sweeper gửi bù); câu UPDATE đó cũng set `game_sessions.ended_at`. **Job hủy ván** (`GameSessionCancelJob`, mỗi phút, **chỉ chạy khi `GAME_SESSION_CANCEL_ENABLED=true`**, mặc định tắt): `UPDATE ... SET status = 'CANCELLED', ended_at = now()` cho ván `RUNNING`, `result IS NULL`, `created_at` cũ hơn `GAME_SESSION_CANCEL_AFTER_MINUTES` (mặc định 5), tối đa 1000 ván / lần, `FOR UPDATE SKIP LOCKED`; chỉ gửi settlement cho ván có subscription chưa hoàn. **Sweeper** (`SettleSweeperJob`, mỗi phút): ván FINISHED / CANCELLED hơn 2 phút (`COALESCE(ended_at, created_at)`) còn subscription đủ điều kiện hoàn, subscription tạo trong 7 ngày; `SET settle_req:{gsid} NX EX 300` trước khi XADD (SET thất bại thì bỏ qua). Có log WARN của sweeper nghĩa là có tín hiệu bị mất.
- Job dùng `setInterval` (không thêm `@nestjs/schedule`: bản hiện tại đòi Node >= 20.19 và kéo theo thay đổi lockfile của web-admin).

### Job dọn dữ liệu & múi giờ — `apps/api/src/jobs/`
- **Múi giờ toàn hệ thống:** `TZ` (mặc định `Asia/Bangkok`, đặt trong `.env`) được `docker-compose.yml` truyền cho MỌI service (db, flyway, redis, api, web-portal, web-admin, ai, crawl-agent-v2). **Code không ghi cứng múi giờ**: `appTimeZone()` (`common/timezone.ts`) đọc `process.env.TZ`; thiếu / sai ⇒ log WARN (một lần) và dùng UTC. Mọi phép chia "ngày" trong SQL (mốc 0h của job, bảng tổng hợp, dashboard 7 ngày) truyền tên múi giờ bằng tham số `AT TIME ZONE $n::text`, không phụ thuộc timezone mặc định của Postgres. (Nếu shell trên host có xuất biến `TZ` thì docker compose lấy giá trị đó thay cho `.env`.)
- **`job_configs` (V4; V5 thêm dòng AI và TẮT hai job dọn dữ liệu):** mỗi job một dòng `(type, value, unit, updated_at)`, **đọc lại ở mỗi lần chạy** (đổi không cần restart). V4 seed `('CLEAR_PREDICT_UNUSE', 2, 'hour')`, `('CLEAR_HISTORY', 7, 'day')`, nhưng **V5 đặt `value = NULL` cho cả hai ⇒ hai job đang TẮT** (job bỏ qua, log DEBUG; chưa xóa dữ liệu nào). Bật lại sau khi xác nhận: `UPDATE job_configs SET value = 2, updated_at = now() WHERE type = 'CLEAR_PREDICT_UNUSE'` / `value = 7 ... 'CLEAR_HISTORY'`. Chỉnh bằng SQL: `UPDATE job_configs SET value = 14 WHERE type = 'CLEAR_HISTORY'` (đổi `unit` tương tự); **tắt** job: `UPDATE job_configs SET value = NULL WHERE type = ...` (bỏ qua, log DEBUG); bật lại: đặt `value` số nguyên > 0. Không có CHECK ở DB: `value <= 0`, `unit` ngoài `minute | hour | day` hoặc thiếu dòng ⇒ job log WARN và bỏ qua lần chạy. **Mốc cắt (`job-config.ts`, dùng chung hai job):** `day` ⇒ 0h (theo TZ) của ngày (hôm nay − value); `hour` / `minute` ⇒ `now() − value` giờ / phút. **Cảnh báo:** `CLEAR_HISTORY.value` < 7 ngày làm dashboard 7 ngày (đọc `transactions`, chưa đọc bảng tổng hợp) mất dữ liệu các ngày cũ.
- **Lịch** (`JobsScheduler`, `setInterval`): `CLEAR_PREDICT_UNUSE` ở phút :00 mỗi giờ, `CLEAR_HISTORY` lúc 03:00 mỗi ngày (theo TZ). **Không có `last_run_at` và không chạy bù**: lỡ một lần (API tắt) thì lần chạy sau tự xử lý phần quá hạn (mốc cắt luôn tính từ lúc chạy). Chống chạy chồng / trùng: khóa Redis `job:lock:{type}` (`SET NX EX`, gia hạn mỗi lô) và dấu `job:fired:{type}:{giờ|ngày}`. Chạy tay (cùng code `JobRunner`, không chờ giờ): `pnpm --filter @toolhackchain/api run-job CLEAR_HISTORY` (hoặc `docker exec -it tool-chain-api node dist/cli/run-job.js CLEAR_HISTORY`).
- **CLEAR_PREDICT_UNUSE:** xóa prediction (CÓ hoặc KHÔNG có pick) thỏa TẤT CẢ: không có `prediction_subscriptions` nào; ván `FINISHED` / `CANCELLED`; `created_at` cũ hơn mốc cắt; không thuộc `PROTECTED_SHOES` = `STATS_SHOES + 1` shoe gần nhất của stream (shoe hiện tại + các shoe quá khứ của biểu đồ "Tỷ lệ win theo phiên", **dùng chung hằng số `STATS_SHOES`** với `predictions.service.ts`, xếp hạng như `stats()`; thêm shoe của prediction mới nhất) nên biểu đồ không đổi. Xóa theo lô 1000, chỉ bảng `predictions`.
- **CLEAR_HISTORY:** xóa **THEO VÁN** mọi `game_sessions.created_at < mốc cắt` và dữ liệu của đúng các ván đó (không xóa từng bảng theo `created_at` riêng). **Không bỏ qua ván nào theo trạng thái** (kể cả ván `RUNNING` treo và subscription "chờ hoàn"): mỗi lần chạy log WARN hai con số tách riêng (số ván RUNNING đã xóa; số subscription `refunded_at IS NULL AND refund_waived_at IS NULL` thuộc ván thua / hủy / RUNNING đã xóa), chỉ để theo dõi. Mỗi lô 500 ván trong MỘT transaction: khóa ván + subscription → **một câu CTE** xóa `transactions` **CHARGE / REFUND** của các subscription đó và ghi đúng những dòng vừa xóa vào `transaction_daily_summaries` (nhóm theo user, loại, ngày CỦA CHÍNH giao dịch theo TZ; `ON CONFLICT DO UPDATE` cộng dồn nên chạy lại không cộng lặp) → xóa `prediction_subscriptions` → `predictions` → `game_sessions`. Lỗi ⇒ rollback lô, log ERROR, dừng job (lần sau làm tiếp). **Quy tắc: chỉ dọn CHARGE / REFUND; TUYỆT ĐỐI không đụng `MINT`, `TRANSFER_OUT`, `TRANSFER_IN`, `INVOKE`** (chỉ CHARGE / REFUND gắn với subscription; câu DELETE chỉ nhận hai loại đó). Bất biến sau khi chạy: (tổng `transaction_daily_summaries` + CHARGE / REFUND còn lại) theo (user, loại) = tổng trước khi chạy; `users.balance` không đổi. Bảng tổng hợp chưa dùng ở giao diện.
- **Tín hiệu rebuild AI:** CLEAR_HISTORY xóa ít nhất một ván ⇒ API `PUBLISH ai:rebuild` (Redis **Pub/Sub**, `AI_REBUILD_CHANNEL` ở `packages/shared/src/ai.ts` ↔ `contract.py`; mất tín hiệu khi AI tắt không sao vì khởi động vẫn dựng từ DB). Trong lúc job clear chạy không tạm dừng gì. AI (`listen_rebuild` → `AiService.request_rebuild` → `rebuild_now`, `service.py`): dùng chung cơ chế dựng lại **nguyên tử, không chặn dự đoán** với đổi `AI_HALF_LIFE` / gần tràn số mũ (xem **Luồng dự đoán AI**): chờ `REBUILD_SETTLE_SECONDS` (env `AI_REBUILD_DELAY_S`, mặc định 5s, để batch ghi DB của ingestion kịp commit), dựng toàn bộ bảng vào key tạm rồi đổi tất cả trong một MULTI/EXEC; dự đoán vẫn chạy bằng bảng cũ, chỉ tạm dừng phần ĐẾM (kết quả mới nằm lại trong `ai:results`); đang dựng hoặc đã có yêu cầu chờ mà có tín hiệu thêm ⇒ bỏ qua. Bảng đếm sau đó chỉ còn dữ liệu của N ngày giữ lại.

### Stream detail realtime (web-portal `/streams/[streamId]`)
- **Kết nối SSE** (`use-live-items.ts`): xin ticket (`POST /realtime/ticket`, `src/lib/api/realtime.ts`) rồi mở `EventSource(/stream?ticket=)`. Trang chi tiết xin ticket với `participate_stream_id` (= tham gia, bị trừ tiền mỗi dự đoán có pick, kể cả tab nền); `items` chỉ để nhận tick (không tham gia). Ticket dùng một lần nên lỗi / server đóng ⇒ đóng EventSource và tự xin ticket mới với backoff 1s → 15s (`reconnectCount` tăng khi mở lại được). 401 (không làm mới được token) ⇒ chưa đăng nhập; 400/403/404 ⇒ `revoked`; 402 `INSUFFICIENT_BALANCE` hoặc event `insufficient_balance` ⇒ `insufficient` (dừng hẳn) và trang chi tiết chuyển về `/categories/:id?notice=insufficient_balance` (danh sách hiện thông báo hết điểm rồi bỏ query). `GET /streams/:id` trả 402 (vào bằng link trực tiếp) ⇒ màn "Không đủ điểm".
- **`stream_id` gắn vào event SSE:** `RealtimeHub.withStreamId()` thêm `stream_id` (UUID DB) vào tick từ cache `stream:{key_id}` (`RealtimeTick` ở `packages/shared`); cache miss ⇒ `null`, **không upsert** (ingestion tạo stream và ghi cache sau khi commit). `CacheWarmup` nạp sẵn cache này từ DB lúc API khởi động. Portal subscribe theo `key_id` (`buildKeyId` ở `packages/shared`, api re-export) và chấp nhận tick nếu `stream_id` khớp HOẶC `null`.
- **Trạng thái ván** (`StreamStatus`): `IN_PROGRESS` (Đang tiến hành), `DONE` (Hoàn tất tiến trình), `GET_RESULT` (Nhận kết quả), `SUMMARY_RESULT` (Tổng kết). Giá trị lạ ⇒ hiển thị trung tính + `console.warn`. Thêm `STARTING_NEW_ROUND` ("Ván mới bắt đầu", **chỉ category sx_lobby, chỉ để hiển thị**): crawler (`SXLobby._update_status`) gán cho message ĐẦU TIÊN (bất kỳ loại nào: Bet / Dealer / RoadInfo / TableInfo) của một (shoe, round) chưa từng thấy khi bàn đã có ván trước, round tăng lên hoặc `= 1`, và message đó không có eventType hợp lệ; lần đầu thấy bàn, round giảm khác 1, hoặc có eventType thì không gán. Các message sau cùng round giữ status, `GP_NEW_GAME_START` ghi đè. Tick mang status này có `actual_result = null`. API: ingestion **không ghi DB**, `predict-trigger` **không** đụng `round_status` / `recent` / `ai:results` / `predict:requests` / phí (không log "status lạ"); chỉ hub đẩy SSE như mọi tick. Không nằm trong `STATUS_RANK` / script `advanceRoundStatus` (`RoundStatus` = `StreamStatus` trừ status này). Ván hiện tại = `(stream_shoe, stream_round)`; sang round mới ⇒ khung kết quả về trạng thái chờ.
- **Kết quả ván = event `round_result`** (hub phát một lần, chỉ đi tới; xem **Phiên và kết quả CHỈ ĐI TỚI**). Portal không tự dò `actual_result` trong tick. Kết quả giữ theo `(shoe, round)`, chỉ hiện ở khung dự đoán khi khớp phiên đang hiển thị.
- **Khung dự đoán** (`PredictionPanel`, `use-prediction.ts`): workflow của một ván **chỉ bắt đầu khi nhận `IN_PROGRESS` của ván đó**. Portal (`usePredictionStats`, gọi cả `/stats` và `/best-streak`) fetch khi vào trang / SSE phục hồi, refetch sau ~4.5s khi có kết quả và ~0.5s khi có event `prediction`.

### Redis Stream consumer
- Tên consumer **cố định**, khai báo qua biến môi trường trong `docker-compose.yml` (ví dụ `CONSUMER_NAME=api-worker-0`).
- **Không dùng `docker compose up --scale`** cho service consumer. Các replica sẽ dùng chung biến môi trường, tức là trùng tên consumer. Cần thêm instance thì khai báo service riêng với tên consumer riêng.
- Khi khởi động: đọc PEL của chính mình (`XREADGROUP ... STREAMS key 0`) cho hết, sau đó mới đọc `>`.
- **Chỉ `XACK` sau khi DB đã commit.**
- Mọi handler phải **idempotent**, vì message có thể được xử lý lại.
- **Giới hạn thời gian:** consumer là vòng lặp tuần tự nên một `await` treo sẽ chặn mọi message. Vì vậy pool pg đặt `connectionTimeoutMillis`, `statement_timeout`, `query_timeout`, `idle_in_transaction_session_timeout`, keepalive (`app.module.ts`); `predict-persist` bọc mỗi message trong `PERSIST_HANDLE_TIMEOUT_MS` (quá hạn ⇒ ném lỗi, loop thử lại từ PEL) và log WARN khi chậm hơn `PERSIST_SLOW_WARN_MS`; kết nối Redis của consumer có `commandTimeout` (> `TRIGGER_BLOCK_MS`) và keepalive.
- Danh sách consumer group hiện có: `persist` (ingestion, trên `ticks`), `predict-trigger`, `predict-persist`, `settle` (api, trên `settle:requests`), `ai-counter`, `ai-predictor` (ai). Mỗi group một consumer cố định (`CONSUMER_NAME` cho api, `AI_CONSUMER_NAME` cho ai).
- **Log:** `API_LOG_DEBUG` (mặc định `false`) điều khiển mức DEBUG của Nest logger (`main.ts`): `false` ⇒ log / warn / error / fatal; `true` ⇒ thêm debug. Log "Prediction ...: <reason> (n kết nối)" khi `pick = null` và "trừ 0 user ... (NO_PARTICIPANTS)" / không có participant là DEBUG. `PredictTriggerService`: **mọi nhánh bỏ qua** (tick không parse được, `data` sai, tên không hợp lệ, shoe/round không phải số nguyên, status lạ, cờ `predict_req` đã có) đều log mức LOG qua `logOnce` (tối đa 1 dòng / phút / khóa); nhánh trùng lặp bình thường (đã gửi kết quả / request, status không tiến) không log.

## Quy tắc bất biến về tiền

Các quy tắc dưới đây **không được phá vỡ**. Nếu một yêu cầu buộc phải vi phạm, hãy dừng lại và hỏi.

1. **Chỉ server quyết định việc thu tiền.** Ack hay bất kỳ tín hiệu nào từ client không bao giờ được dùng để trừ hoặc hoàn tiền.
2. **Trừ tiền trước, giao hàng sau.** `predict_result` chỉ được gửi cho user đã trừ điểm thành công. Lọc event **ở server**, không gửi hết rồi để client tự ẩn.
3. **Trừ tiền là atomic và có điều kiện**, trừ cho cả phòng bằng một câu lệnh:
   ```sql
   UPDATE users
   SET balance = balance - :fee
   WHERE user_id = ANY(:participant_ids) AND balance >= :fee AND status = 'ACTIVE'
   RETURNING user_id, balance + :fee AS balance_before, balance AS balance_after;
   ```
   Sau đó bulk insert `prediction_subscriptions` và `transactions (CHARGE)` **trong cùng một DB transaction**.
4. **Idempotent khi retry:** insert subscription dùng `ON CONFLICT (user_id, prediction_id) DO NOTHING`. Retry không bao giờ được trừ tiền hai lần.
5. **Hoàn tiền ở bước settlement**, ngay khi game_session có result — **chỉ khi env `HAS_REFUND=true`** (mặc định). `HAS_REFUND=false` ⇒ không hoàn trong mọi trường hợp dưới đây (kể cả `CANCELLED`) và subscription được đánh dấu `refund_waived_at` (không bao giờ hoàn nữa, kể cả khi bật lại cờ); ngoại lệ này do chủ dự án quyết định (2026-11-11), không tự mở rộng:
   - Dự đoán sai (`predict_result != result`) thì hoàn `fee_amount` cho mọi subscriber.
   - Session `CANCELLED` thì hoàn cho mọi subscriber.
   - Chỉ cập nhật các dòng có `refunded_at IS NULL`, set `refunded_at` và ghi `transactions (REFUND)` trong cùng một DB transaction.
6. **Chuyển điểm Admin → User:** kiểm tra `admin.balance >= amount`. Ghi 2 dòng `TRANSFER_OUT` và `TRANSFER_IN` trong cùng một DB transaction. **Lock các dòng users theo thứ tự `user_id` tăng dần** để tránh deadlock.
7. Mọi thay đổi `balance` đều phải có dòng `transactions` tương ứng với `balance_before`/`balance_after` khớp nhau.
8. `fee_amount` lưu lại giá tại thời điểm trừ. Không tính lại từ hằng số hiện tại.
9. **Không tính toán trên `balance`/`amount`/`fee_amount`/`balance_before`/`balance_after` bằng `+`, `-`, `Number()` trong TS.** Các cột này là `bigint` nên TypeORM/`pg` trả về **chuỗi**: `"10" + 5` ra `"105"`, còn `Number()` mất độ chính xác khi vượt 2^53. Mọi phép cộng/trừ/so sánh tính **trong SQL** (như câu `UPDATE` ở mục 3); nếu bắt buộc tính ở TS thì dùng `BigInt`, không bao giờ `Number`.

## Participants & SSE

- Participant = kết nối SSE **tham gia** (ticket có `participate_stream_id`, chỉ USER, mỗi kết nối đúng một stream) mở từ trang chi tiết, giữ trong RAM của `ConnectionRegistry` (`realtime/connection-registry.ts`; API chạy một instance). Kết nối chỉ có `items` (trang danh sách) không bao giờ là participant, chỉ nhận tick. Bảng `stream_participants` cũ đã bỏ (V11).
- Mỗi kết nối tham gia một dòng `stream_connections`: INSERT trước khi gửi header (lỗi DB ⇒ 500), UPDATE **đúng một lần** lúc đóng (`closed_at`, `close_reason`, `last_ping_at` — `lastPingAt` chỉ ở RAM cho tới lúc đóng). Lý do: `CLIENT_CLOSED` (`res` close), `PING_FAILED` (ghi lỗi / buffer > 1MB), `INSUFFICIENT_BALANCE`, `SESSION_REVOKED` (`session:{sid}` không còn, hoặc user không còn được trừ), `SERVER_SHUTDOWN` (`beforeApplicationShutdown`, ghi theo lô), `SERVER_RESTART` (lúc khởi động đóng mọi dòng còn mở).
- Ping mỗi 15s (`event: ping`), một timer chung cho mọi kết nối, kiểm tra session bằng một pipeline `EXISTS` (Redis lỗi thì không đóng nhầm). Ghi thành công chỉ nghĩa là kernel / proxy đã nhận: tab nền / tab "ma" sau proxy vẫn bị trừ tới khi kết nối đóng (đã chấp nhận).
- Được tham gia nhiều stream cùng lúc, mỗi stream trừ tiền riêng. Nhiều tab cùng một stream chỉ tính một lần (`participantUserIds` distinct), mọi tab đều nhận pick.
- `balance < fee` thì API gửi event `insufficient_balance` rồi đóng kết nối tham gia của user ở stream đó (ở lần dự đoán kế tiếp không trừ được).

## Auth & bảo mật (`apps/api`)

Mọi route đều yêu cầu đăng nhập, trừ route gắn `@Public()`. Route thực tế có tiền tố `/api`.

### Luồng token
- `POST /api/auth/login` `{ phone_number, password, audience?: "portal" }` → access token JWT (HS256, ~15 phút; claims `sub`=user_id dạng string, `role`, `sid`, `jti`) trong body + refresh token trong cookie `refresh_token` (`httpOnly`, `Secure`, `SameSite=Strict`, `path=/api/auth/refresh`).
- **Portal chỉ cho USER:** web-portal gửi `audience: "portal"`; HOST / ADMIN nhận cùng lỗi 401 như sai mật khẩu (không tạo session, không tính vào số lần sai, log WARN `portal login rejected`). Cookie refresh dùng chung với web-admin (cùng site) nên portal cũng kiểm tra claim `role` của access token sau login / refresh và bỏ phiên không phải USER (chỉ chặn phía UI, API vẫn kiểm tra role từng route). web-admin gửi `audience: "admin"`: chỉ HOST / ADMIN, USER nhận cùng lỗi 401 (`audience` bỏ trống ⇒ không hạn chế).
- `POST /api/auth/change-password` `{ current_password, new_password (12–128 ký tự) }` (mọi role đã đăng nhập, 204, giới hạn 5 lần/phút/IP): sai mật khẩu hiện tại ⇒ 400 (không dùng 401 để client không nhầm là hết phiên), mật khẩu mới trùng cũ ⇒ 400; thành công thu hồi **các phiên khác** của user (`SessionService.revokeOtherSessions`), giữ phiên hiện tại.
- `POST /api/auth/refresh` (đọc cookie) xoay refresh token mỗi lần gọi. Dùng lại token cũ ⇒ thu hồi cả session (phát hiện bị đánh cắp). Không có khoảng ân hạn: hai tab refresh đồng thời có thể làm đăng xuất.
- `POST /api/auth/logout` xóa session + refresh token (Redis) + cookie và **đóng ngay** các kết nối SSE của session đó (`SessionService.onRevoked` → `ConnectionRegistry.closeSession`, lý do `SESSION_REVOKED`; áp dụng cả khi user bị khóa); `GET /api/auth/me` không bao giờ trả `password`, có `display_name` (null = chưa đặt) và `can_participate` (xem **Billing**).
- Redis: `session:{sid}` `{user_id, role, created_at}` (TTL `SESSION_TTL_SECONDS`, sliding), `user_sessions:{user_id}` (set sid), `refresh:{sid}` (hash `current`/`previous`, chỉ lưu HMAC-SHA256 bằng `JWT_REFRESH_SECRET`), `login_fail:{phone}` / `login_lock:{phone}`.
- `SessionGuard` (APP_GUARD, `auth/session.guard.ts`): verify chữ ký + `exp` với thuật toán cố định HS256, rồi kiểm tra `session:{sid}` còn trên Redis và `user_id` khớp `sub`; gắn `req.user = { userId, role, sessionId }`. Thứ tự guard toàn cục: Throttler → SessionGuard → RolesGuard.
- Sai mật khẩu / phone không tồn tại / `status != ACTIVE` ⇒ cùng một lỗi 401. Sai ≥ `LOGIN_MAX_ATTEMPTS` lần ⇒ khóa phone `LOGIN_LOCK_MINUTES` phút (429, tính cả phone không tồn tại). `/auth/login` còn bị giới hạn 10 lần/phút/IP.
- Mật khẩu hash argon2id (`auth/password.ts`). User chuyển sang `DEACTIVE`/`DELETED` ⇒ gọi `SessionService.revokeAllSessions(userId)` (token cũ bị 401 ngay).

### Phân quyền
- `@Roles(...)` + `RolesGuard`; decorator `@Public()`, `@CurrentUser()` ở `auth/decorators.ts`.
- Phạm vi theo `users.refer_user_id` (cấp trên trực tiếp), kiểm tra trong `PermissionService.assertCanManage()`: **ADMIN chỉ thao tác USER có `refer_user_id = admin.user_id`; HOST chỉ thao tác ADMIN có `refer_user_id = host.user_id`**. Không ai thao tác / cấp điểm cho chính mình (`assertCanGrantPoints`). Target không tồn tại hoặc ngoài phạm vi đều trả 403. Mọi API mới thao tác trên user khác PHẢI gọi hàm này.
- **ADMIN chính (`MAIN_ADMIN_USER_ID`) không bị deactive / xóa:** `UsersService.updateStatus` trả 403 khi đổi nó sang `DEACTIVE` / `DELETED` (kích hoạt lại vẫn được); web-admin (`/host/admins`, `sub-admin-table.tsx`) ẩn nút Deactive và Xóa ở dòng của nó. Lý do: nó là cấp trên của mọi user tự đăng ký, không `ACTIVE` thì đăng ký trả 503.
- Xóa (soft delete) do cha làm với con trực tiếp (HOST → ADMIN, ADMIN → USER), chỉ khi con đang `DEACTIVE` (còn `ACTIVE` ⇒ 409) và không còn cấp dưới chưa xóa (409).
- `POST /api/users` `{ phone_number, password (>= 12 ký tự) }`: HOST tạo ADMIN, ADMIN tạo USER. Role do server suy ra từ người gọi (`PermissionService.managedRole`), `refer_user_id` luôn là người gọi; body không nhận `role` / `refer_user_id`. Phone trùng ⇒ 409. `display_name` tùy chọn (1–50 ký tự, trim, không ký tự điều khiển); `PATCH /users/:id` nhận thêm `display_name` (chuỗi = đặt, `null` = xóa), cùng luật cha → con trực tiếp.
- **Tên hiển thị thay số điện thoại:** `display_name` chỉ để hiển thị / che số; đăng nhập, khóa tài khoản vẫn theo `phone_number`. API trả thông tin của người KHÁC cho cấp trên ở chỗ chỉ cần nhận diện (cột "Người cấp") chỉ trả tên, không trả số điện thoại; chưa đặt tên ⇒ null (UI hiện "—"). Danh sách / chi tiết cấp dưới vẫn trả `phone_number` cho cấp trên quản lý họ.

### API danh sách user cấp dưới
`GET /api/sub-admins` (HOST / ADMIN; `users/sub-admins.*`): cây user dưới người gọi — con trực tiếp (`refer_user_id` = người gọi, `depth` 1) và toàn bộ con cháu (recursive CTE trên `refer_user_id`, tối đa 10 cấp, có chống vòng), không gồm chính người gọi, **ẩn user `DELETED`** (cùng nhánh bên dưới; chỉ hiện khi lọc `status=DELETED` rõ ràng; `GET /sub-admins/:id/users` cũng ẩn). Phạm vi chỉ lấy từ token, không nhận id từ client. Query: `page`, `limit` (1–100), `status` (`ACTIVE|DEACTIVE|DELETED`), `role` (`ADMIN|USER`), `q` (số điện thoại hoặc `display_name` chứa chuỗi, không phân biệt hoa thường, 1–50 ký tự); sai kiểu / tham số lạ ⇒ 400. Response `{ items, total, page, limit }` dạng **cây**: `items` là con trực tiếp, mỗi item `{ user_id, phone_number, role, status, balance (chuỗi), refer_user_id, depth, created_at, children[] }` với `children` là con trực tiếp của user đó (đệ quy). `total` / `page` / `limit` tính trên con trực tiếp. Lọc `status` / `role` / `q`: giữ user khớp và mọi tổ tiên của nó (nhánh không có user khớp bị bỏ).

### Sửa user
`PATCH /api/users/:userId` `{ phone_number?, password? }` (HOST / ADMIN, `UsersService.update`; ít nhất một trường, mật khẩu >= 12 ký tự, phone chỉ chữ số 6–20): chỉ **cha sửa con trực tiếp** (`assertCanManage`). Cháu, cha, chính mình, không tồn tại ⇒ 403; user `DELETED` ⇒ 409; phone trùng ⇒ 409. Đổi mật khẩu thu hồi mọi phiên của target. Web-admin chỉ hiện icon sửa / deactive / xóa ở dòng `depth === 1`; deactive và xóa gọi `PATCH /users/:id/status` (`DEACTIVE` / `DELETED`). Xóa (`UsersService.remove`, một DB transaction, khóa users theo `user_id` tăng dần, tính trong SQL; body `{ status: "DELETED", transfer_to_admin_id? }`): điểm còn lại của con được **thu hồi về cha** (hai dòng `INVOKE`), rồi set `DELETED` và đổi `phone_number` thành `<số gốc>_<epoch ms>` (V18, số gốc là phần trước `_`, số được dùng lại cho tài khoản mới); response `{ user_id, status, returned_points, transferred_to }`. ADMIN xóa USER: không nhận `transfer_to_admin_id` (400 nếu gửi), USER còn cấp dưới chưa xóa ⇒ 409. HOST xóa ADMIN: ADMIN không còn cấp dưới chưa xóa ⇒ xóa luôn; còn cấp dưới mà thiếu `transfer_to_admin_id` ⇒ 409 `{ code: "TRANSFER_REQUIRED" }`; có `transfer_to_admin_id` (ADMIN khác, ACTIVE, con trực tiếp của HOST, ngoài ra 403) ⇒ `refer_user_id` của mọi cấp dưới chưa xóa chuyển sang ADMIN đó. web-admin xác nhận xóa trước, chỉ khi nhận `TRANSFER_REQUIRED` mới mở dialog chọn Admin nhận bàn giao. Deactive / xóa đều thu hồi mọi phiên của target (portal gọi `/auth/me` ⇒ 401). Hàng thao tác: ACTIVE ⇒ xem / sửa / cấp điểm / deactive; DEACTIVE ⇒ xem / sửa / kích hoạt / xóa; user `DELETED` không có thao tác ghi. Cả `/host/admins` và `/admin/users` có trang chi tiết (`/host/admins/[id]`, `/admin/users/[id]`).

### API chi tiết user cấp dưới
Cùng `users/sub-admins.*`, HOST / ADMIN, `:id` phải là UUID. Phạm vi: `:id` phải nằm trong cây dưới người gọi (con trực tiếp hoặc con cháu, tối đa 10 cấp); ngoài phạm vi hoặc không tồn tại ⇒ 403.
- `GET /api/sub-admins/:id` → một user `{ user_id, phone_number, role, status, balance, refer_user_id, depth, created_at }` (không có `children`).
- `GET /api/sub-admins/:id/users?page&limit` → `{ items, total, page, limit }`: con trực tiếp của `:id`, mới nhất trước.
- `GET /api/sub-admins/:id/point-transactions?page&limit` → `{ items, total, page, limit }`: điểm `:id` nhận được (`MINT` / `TRANSFER_IN`), mỗi item `{ transaction_id, type, amount (chuỗi), granter_id, granter_name (= `display_name` của người cấp), created_at }`, mới nhất trước. Trang chi tiết admin (`/host/admins/[id]`) dùng cả ba, phân trang ở server.

### API dashboard
`GET /api/dashboard` (HOST / ADMIN; `users/dashboard.*`): số liệu của cây user dưới người gọi (con trực tiếp + con cháu, tối đa 10 cấp, bỏ user `DELETED`; phạm vi chỉ lấy từ token). Response `{ total_users, active_users (status ACTIVE), inactive_7_days (ACTIVE và COALESCE(last_login_at, created_at) cũ hơn 7 ngày), total_unused_points (tổng balance, chuỗi), created_per_day[{date, value}], points_used_per_day[{date, value (chuỗi)}] }`. Hai mảng theo ngày: 7 ngày gần nhất gồm hôm nay (cũ → mới), ranh giới ngày theo múi giờ của process (`appTimeZone()`, biến `TZ`, xem **Job dọn dữ liệu & múi giờ**), ngày không có dữ liệu = 0. `points_used_per_day` = tổng `CHARGE` trừ `REFUND` của các user đó. `users.last_login_at` (V15) cập nhật khi login và khi refresh phiên (tối đa 1 lần / giờ / user, lỗi chỉ log).

### API lịch sử dự đoán của user (web-admin)
`GET /api/admin/users/:userId/prediction-history` và `GET /api/admin/users/:userId/prediction-history/filters` (HOST / ADMIN; `users/user-prediction-history.*`, chỉ ĐỌC). Quyền như trang chi tiết user: gọi `SubAdminsService.detail()` (ngoài cây `refer_user_id` hoặc không tồn tại ⇒ 403); user không phải role USER ⇒ trả danh sách rỗng (stats 0, `win_rate` null).
- **Nguồn:** `prediction_subscriptions` của user JOIN `predictions` → `game_sessions` → `streams` → `categories` → `lobbies`; chỉ ván có dự đoán (`predict_result` khác NULL), `game_sessions.status = 'FINISHED'` và có `result`. Ván không dự đoán / RUNNING / CANCELLED không xuất hiện; lượt xem lucky time (`prediction_user_lucky`) không gồm. Index mới `idx_prediction_subscriptions_user_created (user_id, created_at DESC)` (V6).
- **Query (tùy chọn, AND):** `from`, `to` (ISO, theo `game_sessions.created_at`), `lobby_id`, `category_id`, `stream_id`, `game_shoe`, `game_round` (khớp chính xác), `page`, `limit`. Sắp xếp `game_sessions.created_at` giảm dần.
- **Response:** `{ items[{time, lobby_name, category_name, stream_name, game_shoe, game_round, outcome}], total, page, limit, stats{total_win, total_lose, total_draw, win_rate} }`; `stats` tính trên TOÀN BỘ dữ liệu đã lọc (không phụ thuộc trang). `filters` trả `{ lobbies, categories[+lobby_id], streams[+category_id] }` mà user có dữ liệu.
- **Outcome (tính trong SQL):** `WIN` khi `result = predict_result`; `DRAW` khi `result` thuộc `draw` của file `config/categories` của category (tra theo tên đã chuẩn hóa, `CategoryConfigService.all()` truyền vào SQL dạng JSON; category không có file ⇒ không có hòa); còn lại `LOSE`. **`win_rate = total_win / (total_win + total_lose)`, hòa KHÔNG tính** (khác `win_rate` dùng chung của hệ thống, nơi hòa tính là thắng; không sửa định nghĩa dùng chung); 0 ván thắng + thua ⇒ null.
- **Web-admin:** block "Lịch sử dự đoán" (`components/host/user-prediction-history.tsx`) nằm dưới "Lịch sử cấp điểm" trong `SubAdminDetail`, chỉ hiện khi user là USER; bộ lọc (khoảng thời gian, Sảnh → Game → Bàn phụ thuộc nhau, Số phiên, Số ván), 4 ô thống kê, bảng phân trang ở server. Dữ liệu chi tiết chỉ còn trong thời hạn của job CLEAR_HISTORY.

### Cấp điểm
`POST /api/users/:userId/points` `{ amount }` (HOST / ADMIN, `UsersService.grantPoints`): **chỉ cộng**, **chỉ cho cấp dưới trực tiếp** đang `ACTIVE` (HOST → ADMIN con, ADMIN → USER con). Cháu, cha, chính mình, user không ACTIVE hoặc không tồn tại ⇒ 403 (cùng thông báo). HOST sinh mới (`MINT`); ADMIN chuyển từ balance của mình (`TRANSFER_OUT` + `TRANSFER_IN`, không đủ ⇒ 400 `INSUFFICIENT_BALANCE`). Một DB transaction, khóa users theo `user_id` tăng dần, tính trong SQL. Web-admin chỉ hiện nút cấp điểm ở dòng `depth === 1`.

### API danh mục (chỉ đọc)
`GET /api/lobbies`, `GET /api/categories`, `GET /api/streams` (tạo/sửa nằm ở luồng ingestion, không có API ghi). Mọi role đã đăng nhập đều gọi được.
- Query chung: `page` (>= 1, mặc định 1), `limit` (1–100, mặc định 20), `status` (`ACTIVE|DEACTIVE|ARCHIVE`), `q` (tên chứa chuỗi, không phân biệt hoa thường). Thêm: categories `lobby_id`; streams `lobby_id`, `category_id`. Tham số lạ hoặc sai kiểu ⇒ 400.
- Response `{ items, total, page, limit }`, field snake_case, id là UUID (chuỗi). categories kèm `lobby_name`; streams kèm `category_name`, `lobby_id`, `lobby_name`, `streamer_id` (null nếu chưa có).
- **Số đếm:** lobbies kèm `category_count`, `stream_count`; categories kèm `stream_count` (số nguyên). USER chỉ đếm bản ghi `ACTIVE` (stream phải thuộc category `ACTIVE`); HOST / ADMIN đếm tất cả.
- **Chi tiết:** `GET /api/categories/:id`, `GET /api/streams/:id` (id phải là UUID ⇒ sai thì 400), trả đúng một item như trong list; không tồn tại hoặc không thuộc phạm vi nhìn thấy của role (vd USER với bản ghi không `ACTIVE` / cha không `ACTIVE`) ⇒ 404.
- **USER chỉ thấy bản ghi `ACTIVE`** (bỏ qua `status` truyền vào) và chỉ khi các cấp cha (lobby, category) cũng `ACTIVE`; HOST / ADMIN thấy tất cả và lọc được theo `status`.

### Đăng ký (công khai, tự tạo tài khoản USER)
Portal đăng ký xong dùng được ngay, **không cần Admin duyệt**; bảng `users_register` và toàn bộ luồng cũ (API, trang web-admin "Quản lý người mới") đã xóa (V3). Code ở `apps/api/src/registration/`.
- **Endpoint (`@Public()`):** `GET /api/register/challenge` (30 lần/phút/IP) → challenge ALTCHA; `POST /api/register` `{ phone_number, display_name?, password, confirm_password, altcha }` → `201 { status: "created" }`. Trong một transaction: role USER, `status ACTIVE`, `balance 0`, `display_name` null được (portal hiển thị số điện thoại khi trống), **`refer_user_id = MAIN_ADMIN_USER_ID`** (`packages/shared/src/auth.ts` = `9ba6b144-782a-4eae-a8bd-b1d9f3866285`, hằng số duy nhất, không có hằng số cho role). Hash bằng `ARGON2_OPTIONS` như đăng nhập.
- **Quy tắc dùng chung với ADMIN tạo user:** mật khẩu `@Password()` 12–128 ký tự (`users/dto/password.ts`), tên hiển thị `@DisplayName()` (`users/dto/display-name.ts`). `confirm_password` phải khớp (portal kiểm cả client và server). Số điện thoại của form đăng ký `^\d{6,20}$` (portal tự bỏ khoảng trắng / dấu `-`); **khác** quy tắc tạo user của ADMIN (`@Length(6, 20)`, cho phép chữ), cố ý chưa đồng nhất.
- **ADMIN chính phải tồn tại:** tạo bằng CLI `create-user --role ADMIN --refer-phone <HOST> --fixed-admin-id`. `MAIN_ADMIN_USER_ID` chưa có hoặc không phải ADMIN `ACTIVE` ⇒ `503 { code: "REGISTRATION_NOT_READY" }` + log ERROR (kiểm tra lại trong transaction, khóa `FOR SHARE`).
- **Mã lỗi** (body `{ statusCode, code, message }`, portal ánh xạ sang i18n vi/en): `PASSWORD_MISMATCH` 400, `CAPTCHA_FAILED` 400, `REGISTRATION_FAILED` 400 (số điện thoại đã có tài khoản: cố ý trả thông báo chung "không thể tạo tài khoản với số điện thoại này", không nói rõ lý do; lưu ý vẫn phân biệt được với 201 nên chưa chống hẳn việc dò số, chỉ phụ thuộc captcha + giới hạn IP khi bật chặn), `REGISTER_LIMIT` 429, `REGISTRATION_NOT_READY` 503; sai định dạng khác ⇒ 400 của ValidationPipe. Khi bật chặn và gặp `REGISTER_LIMIT` portal hiện "đã đăng ký quá số lần cho phép hôm nay…" kèm link Telegram nếu `TELE_CONTRACT` hợp lệ.
- **Giới hạn theo IP (Redis, ngưỡng bằng env) — HIỆN CHỈ LOG, KHÔNG CHẶN:** hằng số `ENFORCE_REGISTER_IP_LIMIT = false` ở `registration/registration.limits.ts`; vượt ngưỡng ⇒ vẫn đếm, log WARN `lẽ ra đã chặn: ip=..., count=..., limit=...` và cho đăng ký tiếp (không có biến env cho công tắc này). **Chỉ đổi thành `true` sau khi xác nhận trên server rằng IP trong log `Đăng ký: ip=...` là IP thật của người dùng** (nếu là IP proxy thì mọi người dùng chung một bộ đếm và bị chặn oan). Khi bật: (1) tối đa `REGISTER_MAX_SUCCESS_PER_IP` (5) lần đăng ký **thành công** trong cửa sổ trượt `REGISTER_SUCCESS_WINDOW_HOURS` (24 giờ, tính từ từng lần, không reset theo ngày lịch): ZSET `reg:ok:{ip}`, script Lua kiểm tra rồi `ZADD` một dấu **giữ chỗ TRƯỚC khi tạo user**; tạo user thất bại (trùng số, lỗi DB…) thì `ZREM` đúng dấu đó nên lần lỗi không bị tính và không có khe đồng thời; (2) tối đa `REGISTER_MAX_REQUESTS_PER_HOUR` (20) request `POST /register` / IP / giờ (cửa sổ cố định, `reg:req:{ip}`, guard chạy trước ValidationPipe nên request sai định dạng cũng bị tính). Throttler mặc định 120 lần/phút vẫn áp dụng.
- **Captcha ALTCHA chạy ngầm** (`altcha-lib/v1`, ghim `2.9.0` ở api và portal; **không** dùng API v2 mặc định của gói): API tạo challenge SHA-256 có hạn `ALTCHA_CHALLENGE_TTL_SECONDS` (300), độ khó `ALTCHA_MAX_NUMBER` (mặc định 50000; nghiệm ngẫu nhiên 0..N nên trung bình N/2 lần băm SHA-256; đo ở Node trên i5-8500: ~22 lần băm/ms ⇒ ~1,1 giây trung bình, 200000 thì ~4,5 giây; chưa đo trên điện thoại / trình duyệt thật, tăng N = khó hơn); `verifySolution` kiểm tra chữ ký + hạn + nghiệm, rồi lưu dấu đã dùng `altcha:used:{sha256(payload)}` (SET NX, TTL = hạn + 60s) nên một lời giải chỉ dùng một lần (kể cả khi đăng ký thất bại: portal xin challenge mới mỗi lần gửi). **`ALTCHA_HMAC_KEY` bắt buộc (>= 32 ký tự): thiếu thì API không khởi động.** Portal (`src/lib/altcha.ts` + `altcha.worker.ts`) giải bằng `solveChallenge` trong Web Worker, không render widget; nút hiện "ĐANG XÁC MINH..." lúc giải rồi "ĐANG GỬI...".
- **IP thật (`TRUST_PROXY`):** API dùng `req.ip`; `TRUST_PROXY` bỏ trống = không tin proxy (IP = địa chỉ socket), `1` = sau một nginx, `2` = sau Cloudflare + nginx (nginx phải chuyển IP thật vào `X-Forwarded-For`), hoặc `loopback` / CIDR. Mỗi lần đăng ký log INFO `Đăng ký: ip=...`; IP private / loopback / link-local ⇒ log WARN `proxy chưa cấu hình đúng?`. Repo không có nginx / Cloudflare; trình duyệt gọi API trực tiếp. **Ở local (docker compose) mọi request tới API có cùng IP nội bộ (vd `172.17.0.1`, gateway Docker) nên giới hạn đăng ký tính chung cho cả máy; khi test local đặt ngưỡng cao hơn qua env** (`REGISTER_MAX_SUCCESS_PER_IP`, `REGISTER_MAX_REQUESTS_PER_HOUR`). Sau khi deploy: đăng ký thử từ ngoài rồi xem log API, thấy IP 10.x / 172.x / 192.168.x nghĩa là còn thiếu `TRUST_PROXY`.
- **Portal:** form gồm số điện thoại, tên hiển thị (không bắt buộc), mật khẩu, xác nhận mật khẩu; thành công ⇒ về panel đăng nhập kèm thông báo "Đăng ký thành công"; khối Telegram dưới "Đã có tài khoản?" giữ nguyên.

### SSE
- Event trên một kết nối: `tick` (trạng thái trực tiếp, chỉ đi tới), `round_result` (kết quả ván, chỉ đi tới), `prediction` (chỉ kết nối tham gia), `insufficient_balance`; ping là `event: ping`. Client coi event thiếu `type` là tick.
- `POST /api/realtime/ticket` (cần Bearer) `{ items?: string[] (≤ 20 key_id), participate_stream_id?: uuid }` → `{ ticket, expires_in: 30 }`. `participate_stream_id`: chỉ USER (HOST / ADMIN ⇒ 403), stream trong phạm vi nhìn thấy (404), đủ điểm (402); key_id của stream (dựng bằng `buildKeyId` từ tên trong DB) được thêm vào items. **`items` được lọc theo phạm vi nhìn thấy:** USER chỉ nhận key_id (đã chuẩn hóa) của stream ACTIVE có category + lobby ACTIVE (`StreamsService.visibleKeyIds`, một truy vấn); key_id khác bị bỏ, không còn item nào (và không tham gia stream nào) ⇒ 403; HOST / ADMIN thấy tất cả. Ticket lưu Redis `sse_ticket:{ticket}` `{user_id, session_id, items, participate}` TTL 30s.
- `GET /api/stream?ticket=` là `@Public()` (EventSource không gửi được `Authorization`; tuyệt đối không đưa access token lên query string) nhưng bắt buộc ticket: đọc bằng `GETDEL` (một lần), session phải còn ⇒ sai / hết hạn / đã dùng ⇒ 401. Ticket một lần nên EventSource tự kết nối lại sẽ bị 401 và dừng: client phải tự xin ticket mới (backoff).
- SSE ghi tay bằng `@Res()` (không dùng `@Sse`): header `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`, `flushHeaders()`, socket keepalive. API không dùng middleware nén (nếu thêm thì phải bỏ qua `text/event-stream`). Mọi event ứng dụng là `data: <JSON>` (event mặc định, phân loại bằng `type`: `tick`, `prediction`, `insufficient_balance`); ping là `event: ping`. Đăng ký nghe tick trước rồi mới gửi snapshot `latest:*`.

### Bảo mật chung
Helmet, CORS chỉ cho `CORS_ORIGINS` (`credentials: true`), throttler lưu Redis, `ValidationPipe` global (`whitelist`, `forbidNonWhitelisted`, `transform`), body tối đa 100kb, exception filter global (không lộ stack / lỗi DB), cột `users.password` là `select: false`, không log mật khẩu / token. Thiếu `JWT_SECRET`, `JWT_REFRESH_SECRET`, `REDIS_URL`, `DATABASE_URL`, `CORS_ORIGINS` thì app dừng ngay (`config/env.validation.ts`). `SameSite=Strict` ⇒ ở production web và api phải cùng site.

## Quy ước khi làm việc

- Sửa schema event thì cập nhật cả `contract.py` và `packages/shared/src/realtime.ts`.
- **Schema DB do Flyway quản lý** (`db/migrations/`). Hiện chỉ có 2 file gộp: `V1__init_schema.sql` (toàn bộ schema cuối cùng) và `V2__init_data.sql` (3 role, không có user); sau đó V3 (bỏ `users_register`), V4 (`job_configs` + `transaction_daily_summaries`), V5 (dòng AI trong `job_configs`, tắt hai job dọn dữ liệu); **migration mới bắt đầu từ V6**. Các số `Vn` nhắc trong tài liệu này là tên migration CŨ (đã gộp vào V1). **Mọi DB đã chạy migration cũ (local, server thử nghiệm) phải xóa và tạo lại** (`docker compose down -v` với volume Postgres): giữ `flyway_schema_history` cũ thì Flyway lỗi checksum / version. Đặt tên `V<số>__<mo_ta_snake_case>.sql` (versioned) hoặc `R__<mo_ta>.sql` (repeatable); mỗi file một mục đích, có comment đầu file.
- Mọi thay đổi schema = **một file Flyway mới + sửa entity tương ứng trong cùng commit**. SQL là nguồn sự thật, entity theo SQL.
- **Không bao giờ sửa file migration đã được apply** (kể cả thêm comment, vì Flyway so checksum); muốn đổi thì tạo file mới.
- Không bật `synchronize`, không dùng `flyway clean` (đã `FLYWAY_CLEAN_DISABLED=true`). TypeORM không chạy migration (`migrationsRun: false`).
- **UPDATE / DELETE ... RETURNING qua `ds.query` / `manager.query` / `queryRunner.query` BẮT BUỘC dùng `updateReturning()`** (`apps/api/src/common/update-returning.ts`). Với câu có lệnh chính là UPDATE / DELETE (kể cả `WITH ... UPDATE ... RETURNING`), TypeORM trả `[rows, rowCount]` chứ không phải `rows`: đọc `.map()` / `.length` trực tiếp ra `undefined` / luôn 2 mà không báo lỗi (đã từng làm `settle:requests` mất `game_session_id` và làm `charge` lỗi). CTE có UPDATE bên trong nhưng lệnh chính là INSERT / SELECT thì trả `rows` bình thường: ghi chú `-- top-level: INSERT` (hoặc `SELECT`) ở đầu câu SQL. Lệnh kiểm tra (chạy ở thư mục gốc trước khi merge; in ra vị trí vi phạm và exit khác 0, không in gì = sạch; chỉ bắt SQL viết thẳng bằng template literal trong lời gọi `.query(`):
  ```bash
  git ls-files 'apps/api/src/*.ts' | xargs perl -0777 -ne 'while (/\.query\s*(?:<[^>]*>)?\(\s*`([^`]*)`/g) { my ($sql, $at) = ($1, $-[0]); next unless $sql =~ /\bRETURNING\b/i && $sql =~ /(?<!FOR\s)(?<!DO\s)\b(?:UPDATE|DELETE)\b/i && $sql !~ /--\s*top-level:\s*(?:INSERT|SELECT)\b/i; $n++; printf "%s:%d: UPDATE/DELETE ... RETURNING phai dung updateReturning()\n", $ARGV, 1 + (substr($_, 0, $at) =~ tr/\n//) } END { exit 1 if $n }'
  ```
- Dùng `pnpm`, không dùng npm/yarn. Thêm dependency vào đúng package bằng `pnpm --filter`.
- Không đọc hoặc commit giá trị trong `.env`.
- Không dùng tiếng Việt để đặt tên biến, API, file, module và code liên quan.
